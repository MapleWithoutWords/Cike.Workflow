# Spec: 工作流定义的生命周期管理（保存 / 回滚 / 发布 / 移动）

> Triage: `ready-for-agent`
> 状态：spec 已评审（2026-09-11，需求讨论收敛），待导入 issue tracker

## Problem Statement（问题背景）

流程设计者在画布上编辑工作流后，目前只能修改名称等元数据——画布内容（Body + Options）无处保存。已画好的流程没有"发布"概念，无法区分"草稿"与"可被实例使用的正式版本"；改乱了没有"回滚"手段；定义建错了目录也无法移动。版本数据结构（一行一版本、DefinitionId 聚合、IsLatest/IsPublished 标记）已经存在，查询侧也已为"草稿领先于已发布版本"的场景做了展示，但驱动这些状态流转的四个写操作全部缺失。

## Solution（解决方案）

为工作流定义补全四个写操作，形成完整的版本生命周期：

- **保存**：草稿就地更新——最新版未发布时直接覆盖当前行内容；最新版已发布时生成 v+1 新草稿（版本号增长的唯一路径）。
- **回滚**：用指定历史版本的内容覆盖当前草稿（无草稿则先生成 v+1 草稿），版本号与元数据不动，非破坏性。
- **发布**：只能发布最新行，就地打 IsPublished 标记并记录备注/发布人/时间；发布前做严格画布校验，坏流程不允许上线。
- **移动**：同工作空间内换目录，该定义的所有版本行一起移动。

发布后的历史版本标记全部保留，运行中实例引用的旧版本不受任何操作影响。

## User Stories（用户故事）

**保存**

1. As a 流程设计者, I want 保存画布内容（节点、连线、变量、选项）, so that 编辑进度不会因为关闭页面而丢失。
2. As a 流程设计者, I want 保存未画完的半成品流程, so that 我不必一次画完就能保存进度、下次继续。
3. As a 流程设计者, I want 在流程已发布后继续编辑并保存, so that 线上版本不受影响，我的修改进入新草稿。
4. As a 流程设计者, I want 反复保存草稿时不产生新版本号, so that 版本列表不会被每次 Ctrl+S 刷爆。
5. As a 流程设计者, I want 保存时得到明确的序列化错误提示, so that 结构损坏的画布不会静默存进去。
6. As a 流程设计者, I want 系统内置流程的保存被拒绝, so that 内置流程不会被误改。
7. As a 流程设计者, I want 只读流程的保存被拒绝, so that 被锁定的流程内容不会被改动。
8. As a 流程设计者, I want 保存接口只负责画布内容, so that 改名、改描述等元数据操作不会和内容保存互相干扰。

**回滚**

9. As a 流程设计者, I want 把流程回滚到任意历史版本, so that 改乱之后能快速恢复到已知良好的状态。
10. As a 流程设计者, I want 有未发布草稿时回滚直接覆盖草稿且版本号不变, so that 版本历史保持干净。
11. As a 流程设计者, I want 最新版已发布时回滚生成新草稿, so that 已发布版本永不被改写。
12. As a 流程设计者, I want 回滚只还原画布内容而保留当前名称等元数据, so that 我不需要回滚后再补改一遍元数据。
13. As a 流程设计者, I want 回滚到当前版本时得到提示, so that 我能意识到这是一个无意义操作并纠正目标。
14. As a 流程设计者, I want 系统内置流程的回滚被拒绝, so that 内置流程不被篡改。
15. As a 流程设计者, I want 只读流程的回滚被拒绝, so that 锁定的流程内容保持不变。

**发布**

16. As a 流程设计者, I want 发布我的最新草稿, so that 该流程可以被实例化使用。
17. As a 流程设计者, I want 发布时填写版本备注, so that 团队成员能知道这一版改了什么。
18. As a 流程设计者, I want 发布时系统校验画布完整性（开始节点存在、无孤立节点、变量定义合法、活动必填属性齐全）, so that 坏流程不会流到线上。
19. As a 流程设计者, I want 发布失败时得到具体是哪个节点、什么问题的错误信息, so that 我能直接定位并修复。
20. As a 流程设计者, I want 已发布的最新版再点发布被拒绝并提示先保存出新草稿, so that 避免重复发布造成误解。
21. As a 流程设计者, I want 历史已发布版本的标记在后续发布后依然保留, so that 审计时能看到完整的发布轨迹。
22. As a 工作流管理员, I want 在版本列表中看到每个版本的发布状态、发布人、发布时间和备注, so that 我能审计谁在何时发布了什么。

**移动**

23. As a 流程设计者, I want 把工作流定义移动到同工作空间的其他目录, so that 随着流程数量增长仍能保持清晰的组织结构。
24. As a 流程设计者, I want 移动后该定义的所有版本一起进入新目录, so that 版本历史和定义永远在同一位置。
25. As a 流程设计者, I want 移动到不属于本工作空间的目录时被拒绝, so that 数据不会串到别的空间。
26. As a 流程设计者, I want 系统内置流程的移动被拒绝, so that 内置流程的位置保持稳定。

**通用 / 查询侧联动**

27. As a 流程设计者, I want 上述所有操作失败时收到友好的中文错误提示, so that 我不需要看日志就知道哪里出了问题。
28. As a 流程设计者, I want 通过版本列表和详情接口看到保存/回滚/发布操作后的最新状态, so that 我能确认操作已生效。
29. As a 工作流管理员, I want 系统内置流程的修改类操作被统一拦截, so that 内置流程只能由系统升级来变更。

## Implementation Decisions（实现决策）

**版本模型（沿用现状，不新增表）**

- `WorkflowDefinition` 一行一个版本；`DefinitionId` 聚合所有版本；`Version` 递增；`IsLatest` 唯一指向最新行；`IsPublished` 可存在于多行（当前发布版 = 已发布行中 Version 最大者）。
- 不引入独立的"草稿表"或"发布快照表"，草稿就是那行 `IsLatest && !IsPublished` 的记录。

**保存（Save）**

- 入口 DTO 为画布内容（Body + Options），不含名称等元数据——元数据变更继续走已有的 Update 命令。
- 最新行未发布：就地覆盖该行的画布内容，Version、IsLatest、IsPublished 不变。
- 最新行已发布：新建 v+1 行，IsLatest 转移到新行，新行 IsPublished=false，元数据（名称、描述、类型、目录、系统标记等）沿用最新行。
- 校验宽松：只要求 Body 能通过活动序列化器正常序列化（往返校验），不校验画布业务完整性。
- 拦截规则：`IsSystem` 或 `IsReadonly` 的定义拒绝保存。

**回滚（Rollback）**

- 入参：当前定义的 id + 目标版本（或目标版本行 id）。
- 存在未发布草稿（最新行 !IsPublished）：用目标版本的画布内容覆盖草稿行，版本号不变。
- 不存在草稿（最新行已发布）：新建 v+1 草稿，内容复制自目标版本。
- 只复制画布内容（OriginalStringData + Options），名称等元数据保持当前值。
- 目标版本与当前行为同一行时拒绝（无意义操作）。
- 拦截规则：`IsSystem` 或 `IsReadonly` 拒绝回滚。
- 已接受的取舍：回滚覆盖草稿时，原草稿内容直接丢弃（从未发布过，无历史可寻回）。

**发布（Publish）**

- 只能发布 `IsLatest` 行（按定义 id 定位），就地打标：`IsPublished=true`，记录 `PublishedNote`（选填，512 上限沿用现状）、`PublishedBy`（取当前登录用户）、`PublishedAt`。
- 严格画布校验，全部通过才落库：存在开始节点、无孤立节点、变量定义合法、活动必填属性齐全；校验失败返回 400 并给出可定位的错误描述。
- 画布校验作为引擎层（Core）的新抽象（如 WorkflowValidator），不写在应用层 handler 里——Core 拥有活动模型，校验规则应随引擎演进。
- 最新行已是发布态时拒绝，提示需先保存产生新草稿。
- 拦截规则：`IsSystem` 拒绝发布（与修改/删除的拦截保持一致）。

**移动（Move）**

- 入参：定义 id + 目标目录 id（0 表示根目录，与新增语义一致）。
- 校验目标目录存在且属于同一工作空间。
- 一次性更新该 `DefinitionId` 所有版本行的 FolderId。
- 拦截规则：`IsSystem` 拒绝移动。`IsReadonly` 不拦截（移动不改内容）。

**API 契约**

- 四个新命令 + handler 方法，沿用现有 Command / LocalEventHandler / `ILocalEventBus` 模式。
- 端点注册在 Minimal API 服务中，路径延续 `/api/v1/workflow-definitions` 资源约定；开启自动验证（AutoValidation）。
- 业务错误统一以 UserFriendlyException 抛出（框架转为 400 + 中文消息）。

**Schema 变更**

- 将 `(DefinitionId, Version, IsDeleted)` 索引升级为唯一索引，作为"发布后首次保存并发创建 v+1"的并发兜底；需要相应 EF 迁移。
- 除该索引外无表结构变更（Options 的 json 影子列等已存在）。

**不做的并发处理**

- 不做乐观并发 token / 编辑锁 / "他人已修改"友好提示；并发冲突由唯一索引兜底为最后写入胜出或唯一冲突报错，本期内不做更精细的处理。

## Testing Decisions（测试决策）

- **唯一测试接缝：HTTP API**。所有测试通过 `WebApplicationFactory<Program>` 起真实 host，用 `CreateClient()` 调用四个新端点；状态断言一律通过已有查询端点（版本列表、详情）完成，不直接查 store、不注入服务绕过 HTTP 层。
- 好的测试只断言外部可见行为：HTTP 状态码、响应体、以及经查询端点观察到的状态变化；不断言内部实现（如具体哪行被 Update、序列化细节）。
- 画布校验器不单独开测试接缝，全部通过"发布接口返回 400 + 错误消息"验证其外部行为。
- 测试数据准备同样走 API（先建工作空间、目录、定义），不做直接数据库播种。
- 测试模块与先例：`Backend/tests/Cike.Workflow.Test`（集成测试项目），先例为 `ExampleTest`；沿用 NUnit + `BaseIntegrationTest` 基类；命名遵循 `{Method}_{Condition}_{ExpectedResult}` 且条件用中文（如 `Publish_缺少开始节点_返回400`）。
- 集成测试依赖本地 MySQL 与 Redis（沿用项目现状，测试项目有自己的 appsettings.Development.json 模板）。
- 并发唯一索引兜底不做 HTTP 级测试（难以稳定构造竞态），由 schema 约束保证。

## Out of Scope（范围外）

- 前端交互（编辑器保存快捷键、发布对话框、版本对比 UI、目录树拖拽）——本 spec 仅后端。
- 跨工作空间移动定义。
- 撤销发布 / 版本下线（unpublish / retract）。
- 批量移动多个定义。
- 版本对比 / diff 视图接口。
- 发布事件广播 / 通知（其他模块感知"新版本已发布"）。
- 工作流实例运行时如何解析"当前应使用的版本"（实例启动时的版本选择策略属于引擎运行时范畴）。
- 版本保留策略 / 历史版本自动清理。
- 协同编辑与并发友好提示（仅唯一索引兜底）。
- 保存草稿的自动暂存 / 定时快照。

## Further Notes（补充说明）

- 五个关键决策（版本策略：草稿就地更新；发布：仅最新版就地打标；回滚：覆盖当前草稿；移动：仅同工作空间；校验：保存宽松、发布严格）均已与需求方逐项确认（2026-09-11）。
- "发布后再次保存生成 v+1"是版本号增长的唯一路径，版本列表中版本数 = 发布次数 + 1（首次 Add 的 v1 除外）。
- 已发布版本在后续操作中永不被改写，回滚/保存只作用于未发布草稿行——这是整个模型不变式，测试应覆盖这一点的回归。
- 发布校验器的具体规则清单（开始节点、孤立节点、变量、必填属性）建议在 design 阶段结合 Core 层现有活动模型（Flowchart / Activity 抽象）细化，spec 只锁定"严格校验 + 可定位的错误信息"这一行为契约。
- spec 暂落本地文件（gh CLI 未安装）；导入 issue tracker 时应用 `ready-for-agent` 标签，无需额外 triage。
