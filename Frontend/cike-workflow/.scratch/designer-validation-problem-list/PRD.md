# PRD: 工作流设计器问题清单（画布校验）

Status: ready-for-agent

## Problem Statement

流程设计者在设计器里配完一个节点、或准备发布时，无法确知画布到底有没有问题：没有统一、可定位的错误反馈。现有的客户端提示（missingStartNode 黄条）只检查当前下钻层、只认开始节点，与后端发布时的严格校验口径不一致，常出现"本地看着没问题、一发布就被后端拒"。而后端拒绝时返回的是一坨拍平的文字，无法定位是哪个节点、哪条连线、哪个变量出的问题。设计者被迫反复"发布→读错误→猜节点→改→再发布"，排查成本高、反馈滞后。

## Solution

在设计器画布下方新增一个可折叠的"问题清单"面板，作为画布校验问题的唯一出口：

- 校验规则完全走后端 `ValidateCanvas`（与发布同一套严格规则、递归整棵活动树），前端不再自行判定。
- 编辑时（新增/修改节点、连线、节点表单、变量）自动防抖校验；点发布前预校验；打开画布后校验一次。
- 有问题时：面板逐条列出校验问题（消息 + 节点名），画布上对应节点打红色错误标记；点击清单中可定位的问题会自动下钻到该节点所在容器层并选中高亮。
- 点发布：先校验——有错就不发布、展开清单并跳到首个问题；无错才弹出发布备注框。
- 移除只看当前层的 missingStartNode 黄条及其对发布按钮的禁用，消除双轨矛盾信号。

## User Stories

1. 作为流程设计者，我想在配完一个节点后自动看到它有没有问题，以便即时修正而不必等到发布。
2. 作为流程设计者，我想在画布下方的问题清单里集中看到当前画布的所有校验问题，以便一眼掌握整体健康度。
3. 作为流程设计者，我想让每条问题显示文字消息，以便知道具体错在哪。
4. 作为流程设计者，我想让每条问题显示所属节点的名称，以便快速认出是哪个节点。
5. 作为流程设计者，我想点击清单里的某个问题就自动跳到并选中对应节点，以便不用手动在画布上找。
6. 作为流程设计者，当出问题的节点在我尚未打开的下钻层里时，我想点击问题能自动下钻到那一层，以便直达问题节点。
7. 作为流程设计者，我想在画布上看到出问题节点的红色错误标记，以便不打开清单也能定位。
8. 作为流程设计者，我想在连续编辑时把校验请求合并（防抖），以便不被频繁请求打扰、界面不卡顿。
9. 作为流程设计者，我想在新增节点/连线、修改节点表单、改变量后自动重新校验，以便清单始终反映最新画布。
10. 作为流程设计者，我想在打开一个已有定义时先自动校验一次，以便立刻知道载入的画布是否已存在问题。
11. 作为流程设计者，我想在点发布时先做一次校验，有问题就不发布并把清单展开、跳到第一个问题，以便发布前把问题清干净。
12. 作为流程设计者，我想在画布没有任何问题时点发布能直接进入发布备注框，以便顺畅发布。
13. 作为流程设计者，当校验全部通过时，我想看到"校验通过"的正反馈（且清单自动收起），以便确认可以安心发布。
14. 作为流程设计者，我想把问题清单折叠起来腾出画布空间，以便专注画图，需要时再展开。
15. 作为流程设计者，我想让问题清单显示问题数量，以便不展开也知道有几处要改。
16. 作为流程设计者，对于无法定位到具体节点的工作流级问题（如变量非法），我想在清单里看到它、并知道它不可点击跳转，以便去对应入口（变量对话框）修改。
17. 作为流程设计者，我想让校验只读、不产生版本、不改动我的草稿，以便随意编辑校验都不怕误存。
18. 作为流程设计者，在只读模式（查看历史版本或实例运行轨迹）下，我不想被校验和问题清单打扰，以便安静查阅。
19. 作为流程设计者，当撤销/重做后，我想让问题清单自动刷新，以便反映回退后的画布状态。
20. 作为流程设计者，当发布被后端硬闸门拒绝时，我想让清单自动回填后端返回的结构化问题，以便看到到底哪些节点没过，而不是只有一句拍平的错误。
21. 作为流程设计者，当后端不可用/校验请求失败时，我想看到明确的传输错误提示（而非清单空白被误读为"没问题"），以便区分网络故障与画布正确。
22. 作为流程设计者，我想让问题清单与节点错误标记的口径与后端发布校验完全一致，以便"清单说没问题"就等于"能发布成功"。
23. 作为前端开发者，我想让校验规则的唯一真源在后端、前端不复制任何规则，以便避免双源漂移和矛盾提示。
24. 作为前端开发者，我想让前端计算的活动 NodeId 与后端物化的 NodeId 逐字一致，以便用 NodeId 承载层级定位、前后端对齐。
25. 作为前端开发者，我想复用已有的"活动 Id → 视觉状态叠加"机制来打错误标记，以便不新造一套渲染管线。
26. 作为前端开发者，我想复用已有的命令栈/投影/下钻基础设施来触发校验与定位，以便改动集中、可测。
27. 作为审阅者，我想让问题清单成为校验问题的唯一呈现出口（移除 missingStartNode 黄条），以便不被两套口径打架。

## Implementation Decisions

- **校验真源与契约（ADR 0002）**：走后端 `POST /api/v1/WorkflowDefinitions/ValidateCanvas`，请求 `{ root: 画布根(wire), options: 已存选项(含变量) }`，响应 `WorkflowCanvasValidationErrorDto[]`，每条 `{ activityId?, nodeId?, name?, message }`；空数组即通过；全部为错误级（无 severity）。经 `pnpm api:update` 生成 SDK 方法 `postApiV1WorkflowDefinitionsValidateCanvas`。
- **前置阻塞**：后端需重新生成并重启——当前 `localhost:5046` 跑的是旧构建（`WorkflowInstanceService` 两个 `GetAsync` 路由冲突致 swagger 500；源码已改名 `GetLogsAsync`），否则 SDK 无法生成、阶段 B 起无法编译。此为"重启即可"的构建陈旧问题，非代码改动。
- **移除客户端闸门（ADR 0002）**：删掉 missingStartNode（只看当前下钻层、只认 Start 类型）及其对发布按钮的禁用、头部黄条、发布对话框警告。问题清单为校验问题唯一出口；顶部传输错误条只保留传输/持久化错误。
- **触发时机**：① 编辑（新增/删除节点、连线/断线、移动、属性表单编辑、变量编辑）后在命令执行的统一出口防抖（约 500ms）重校验；② 撤销/重做后重校验；③ load 后校验一次（非阻塞）；④ 发布点击前预校验（阻断式）。只读模式不校验。
- **竞态处理**：以递增请求序号只采纳最新一次校验结果，防止慢响应覆盖新结果。
- **NodeId 计算（ADR 0003）**：`nodeId = 父nodeId + ":" + 自身活动 Id`（根节点即自身 Id），与后端 `ActivityNode.NodeId`（祖先活动 Id 以 `:` 连接再接自身 Id）逐字一致。**成本模型（已核实：后端端口按"包含关系"解析、连线不入图）**：① 新增节点 O(1)——由父 nodeId 直接算，不遍历树；② 连线/断线/移动/改属性不改 nodeId（O(0)）；③ 加载时把 nodeId 计算**折进反序列化本就要做的整树递归**（沿现有 `activities`/`body`/`root` 子形态下传父 nodeId），无独立回填遍历、无额外一趟；④ 跨容器 reparent 会变 nodeId，但当前无此能力。
- **定位下钻**：`revealActivity` 直接**解析校验问题回带的 `nodeId`**（按 `:` 拆分即得祖先活动 Id 链），据此从画布根沿链下钻、复用既有下钻基础设施重建 drill 栈并选中目标——无需全树搜索；`nodeId` 缺失时才回退按 `activityId` 树搜。找不到返回 false（清单中表现为不可点击）。
- **节点错误标记**：复用投影（projection）已有的按 activityId 富化机制，为节点数据增加 `hasError`；节点渲染红色错误标记，与选中态（primary 描边）视觉区分。
- **问题清单面板**：画布下方全宽可折叠 dock（IDE Problems 面板风格；已调研 Camunda Modeler / bpmn-io / VS Code / n8n）。头部=错误数 + 折叠切换 + 校验中态；体=可滚动行列表（图标 + 消息 + 节点名）；可定位行可点、工作流级行只展示；空态="校验通过"并自动折叠。使用既有 ui/ 组件 + lucide 图标 + 主题 token。
- **发布流程**：点发布 → 校验中 → 有错（不发布 + 展开清单 + reveal 首个可定位问题）/ 无错（弹备注框 → 确认 → Publish）；后端 Publish 仍抛 `UserFriendlyException` 时，catch 内重跑 validate 回填结构化清单，并保留原始消息作传输错误兜底。
- **无 schema / 后端契约变更**：仅前端消费既有 `ValidateCanvas`。

## Testing Decisions

- **好测试只测外部行为**：经 composable 暴露的 ref（`problems` / `validating` / `readonly` / `selectedActivityId` / drill 栈）与"哪些 API 以什么 body 被调用"来断言，不断言内部实现细节。
- **测试缝（两个，均为既有缝，优先复用、不新增更低层缝）**：
  1. **composable 缝（主，最高）**：`useWorkflowDesigner` 的既有测试——先例 `useWorkflowDesigner.test.ts`（顶部注释即声明此缝；用 `vi.mock("@/api/generated")` 把生成客户端换成 spy）。新增把 `postApiV1WorkflowDefinitionsValidateCanvas` 加入 mock。覆盖：load 后触发一次校验、编辑/撤销/重做触发防抖校验、validate 写入 problems、只读模式不调用、发布预校验（有错不调 Publish / 无错才调）、Publish 被后端拒后回填、addNode 后 nodeId 正确、revealActivity 下钻到嵌套节点并选中。命名沿用三段式 `Action_Condition_Expected`。
  2. **纯核心缝**：NodeId 纯函数单测——先例 `execution.test.ts`。覆盖 `computeNodeId`（根=自身 Id、`父:子` 拼接）与反序列化 `fromWireActivity` 在既有递归中内联算出整树 nodeId（容器 `activities`、`For/While/ForEach.body`、`Composite.root`、多层嵌套，断言与后端 `:` 方案逐字一致）；以及 reveal 由 `nodeId` 解析祖先链命中/未命中。
- **UI（面板/标记/布局/发布交互）无自动化缝**（代码库无 `.vue` 测试先例），按既有做法在 5173 单一 dev server 做浏览器验证。
- 防抖用假定时器（`vi.useFakeTimers`）驱动，不为测试改生产时序。

## Out of Scope

- 后端校验规则本身的增改（开始节点/孤立节点/连线引用/必填输入/变量合法性的判定逻辑）——沿用既有 `ValidateCanvas`。
- 后端 swagger 500 的代码修复——旧构建问题，重启即可，不在本 spec 改后端代码。
- 警告级（severity）分级、问题分组/排序/筛选、忽略或静默某条问题——当前后端全为错误级，不做分级 UI。
- 跨容器移动（reparent）后的 NodeId 重算——当前无 reparent 能力（见 ADR 0003 Consequences），留待引入该能力时处理。
- 变量对话框自身的即时校验 UI——变量非法由画布校验以工作流级问题呈现，定位到变量入口即可。
- 实例运行轨迹视图的错误叠加——那是执行状态（execution），与画布校验是两套机制。

## Further Notes

- 术语遵循根 / 前端 `CONTEXT.md`：画布校验、问题清单、校验问题、节点 Id（NodeId）、活动 Id、画布根、下钻、只读模式、发布。
- 尊重 ADR 0001（活动自校验、校验器只触发）、0002（校验以后端为唯一真源、移除客户端闸门）、0003（前端计算 NodeId、与后端同构）。
- 根 `CONTEXT.md` 的 NodeId 定义（"创建方不填"）与 ADR 0003 冲突，需在根/后端仓库同步修订。
- 实施按阶段推进：A NodeId 计算 → B 校验状态与触发 → C 定位下钻 → D 节点标记 → E 面板与布线；每阶段可独立 build/test。非机械改动预计 >500 行，已按阶段拆分。
- 完成后更新项目记忆：设计器"校验/问题反馈"能力自此建立；记录"前端 NodeId 须与后端同构"这一长期约束。
